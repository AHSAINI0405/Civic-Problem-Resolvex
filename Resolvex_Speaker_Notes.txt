SLIDE 1 - TITLE SLIDE: RESOLVEX
------------------------------------------------------------------------

PROJECT NAME: Resolvex - Civic Problem Management System

WHAT IS THIS PROJECT?
  Resolvex is a website (web application) where:
  - Citizens report civic problems (broken roads, no water, streetlights, sewage)
  - Government departments see the problems and fix them
  - An Admin manages everything in the system
  - AI automatically understands what type of problem is reported

LANGUAGE USED:
  JavaScript - used for BOTH the frontend (browser) AND backend (server)
  This is called a "Full-Stack JavaScript" application.

KEY TECHNOLOGIES:
  Frontend  : React.js  (builds what users see in the browser)
  Backend   : Node.js + Express.js  (the server / API)
  Database  : MongoDB  (stores all data - users, complaints, departments)
  AI        : Google Gemini API  (auto-classifies complaints with AI)
  Real-Time : Socket.io  (live notifications without refreshing the page)
  Maps      : Leaflet.js  (interactive map for pinning problem location)
  Uploads   : Multer + Cloudinary  (image and video file uploads to cloud)
  Email     : Nodemailer  (sends verification and reset emails)
  Scheduling: node-cron  (runs automatic SLA check every hour)

HOW TO RUN THE PROJECT (for examiner/demo):
  Terminal 1: cd server  ->  npm install  ->  npm start    (port 5000)
  Terminal 2: cd client  ->  npm install  ->  npm run dev  (port 5173)
  Browser: http://localhost:5173

  Demo Login Accounts:
  Admin    : admin@civic.com    / password
  Citizen  : citizen@civic.com  / password
  Dept     : dept@civic.com     / password

SLIDE 2 - PROBLEM STATEMENT
------------------------------------------------------------------------

WHY DID I MAKE RESOLVEX?

  PROBLEM 1 - No Easy Way to Report:
    Most citizens have NO digital platform to report civic problems.
    They have to physically visit offices or make phone calls.
    This is inconvenient, slow, and often ignored.

  PROBLEM 2 - No Tracking System:
    Even when someone reports a problem, there is NO WAY to track it.
    Citizens do not know if their complaint was received, being worked on,
    or completely ignored.

  PROBLEM 3 - Wrong Department Assignment:
    A road problem should go to Roads Department.
    A sewage problem should go to Sanitation Department.
    Without a smart system, complaints go to wrong departments,
    causing delays and confusion.

  PROBLEM 4 - No Data or Accountability:
    Government has NO DASHBOARD to see:
    - Which areas have the most problems
    - Which departments resolve complaints fastest or slowest
    - How many complaints missed their resolution deadline

  RESOLVEX solves ALL FOUR problems with one digital platform.

SLIDE 3 - KEY FEATURES
------------------------------------------------------------------------

FEATURE 1 - AI Auto-Classification (Google Gemini API):
  Citizen types complaint title and description.
  Clicks "Analyze & Auto-Classify" button.
  Google Gemini AI reads the text and returns:
    - Category  : roads / water / sanitation / electricity / etc.
    - Priority  : low / medium / high
    - Confidence: e.g. 85% (how sure the AI is)
    - Suggestion: "Please add your street address to help the team"

  Citizens open a real interactive map.
  They can:
    - Click "Detect My Location" -> GPS auto-detects coordinates
    - Type an address and search
    - Click anywhere on map to drop a pin
  Coordinates saved with complaint so department knows where to go.
  Library: Leaflet.js + react-leaflet + OpenStreetMap tiles (all free)

FEATURE 3 - Real-Time Notifications (Socket.io):
  When admin updates complaint status -> citizen gets notification INSTANTLY.
  When admin assigns complaint -> department gets notified INSTANTLY.
  No page refresh needed. Like WhatsApp messages arriving in real-time.
  Library: Socket.io (WebSockets)

FEATURE 4 - Admin Analytics Dashboard (Recharts):
  Admin sees KPI (Key Performance Indicator) cards + charts showing:
    - Total, Pending, Resolved, SLA Breached complaints
    - Status distribution charts
    - Department performance data
  Library: Recharts

FEATURE 5 - Department Management:
  Admin creates government departments (Roads Dept, Water Dept, etc.)
  Assigns complaints to the correct department.
  Each department only sees their own assigned complaints.

FEATURE 6 - Email Verification (Nodemailer):
  When someone registers, a verification email is sent.
  They must click the link in the email to activate their account.
  This prevents spam and fake accounts.
  Library: Nodemailer

SLIDE 5 - SYSTEM ARCHITECTURE
------------------------------------------------------------------------

HOW THE SYSTEM WORKS (Simple Explanation):

  The application has THREE main parts:

  1. FRONTEND (React + Vite) - Port 5173:
     This is what the user sees in the browser.
     Built with React.js components (reusable UI pieces).
     Communicates with backend via HTTP requests (Axios).
     Keeps a live WebSocket connection for real-time updates (Socket.io).

  2. BACKEND (Node.js + Express) - Port 5000:
     This is the brain/server of the application.
     Handles all business logic (validate, authenticate, process).
     Connects to external services: MongoDB, Gemini AI, Cloudinary, Email.
     Runs Socket.io for real-time communication.
     Runs a cron job every hour to check SLA deadlines.

  3. DATABASE (MongoDB):
     Stores everything: users, complaints, departments, notifications.
     Hosted on MongoDB Atlas (cloud version - always online).

  EXTERNAL SERVICES:
  - Google Gemini AI  : complaint classification and chatbot
  - Cloudinary CDN    : stores uploaded images and videos
  - Nodemailer/Gmail  : sends verification and reset emails
  - OpenStreetMap     : provides map tiles for Leaflet.js

  DATA FLOW EXAMPLE (citizen submits complaint):
  Browser -> React form -> Axios POST to /api/complaints -> JWT check ->
  Multer reads files -> Cloudinary stores images -> Gemini AI classifies ->
  Mongoose saves to MongoDB -> Socket.io notifies admin -> Response to browser

SLIDE 6 - USER ROLES (Three Types of Users)
------------------------------------------------------------------------

THE SYSTEM HAS THREE USER TYPES:

1. CITIZEN (General Public):
   - Creates an account and verifies email
   - Reports civic problems with photos, videos, and map location
   - Uses AI to auto-classify their complaint
   - Sees ONLY their own complaints (privacy protected)
   - Tracks status: Pending -> Assigned -> In Progress -> Resolved
   - Can upvote other complaints and add comments
   - Receives real-time notifications when status changes

2. ADMIN (Government Administrator):
   - Sees ALL complaints from ALL citizens in the system
   - Assigns complaints to the correct department
   - Updates complaint status with remarks
   - Blocks or unblocks any user account
   - Creates and manages government departments
   - Views full analytics dashboard (charts, KPI cards)
   - Monitors SLA breaches (complaints that missed deadline)

3. DEPARTMENT (Government Staff):
   - Sees ONLY complaints assigned to THEIR department
   - Cannot see another department's complaints
   - Accepts complaint -> works on it -> uploads proof photos -> marks resolved
   - Receives instant notifications when complaints are assigned
   - Views their own performance statistics

HOW ROLE-BASED ACCESS CONTROL (RBAC) WORKS:
  After login, server gives a JWT token.
  The token contains: userId, role (citizen/admin/department)
  
  Every API request includes this token in header:
  Authorization: Bearer <token>
  
  Two middleware functions in server/middleware/auth.js:
  - protect(req,res,next)      : verifies token is valid (user is logged in)
  - authorize('admin')         : checks role matches required role
  
  If wrong role  -> 403 Forbidden response
  If no token    -> 401 Unauthorized response
  In React       -> ProtectedRoute component redirects to /login

  REST = Representational State Transfer
  The frontend sends HTTP requests to specific URLs (endpoints).
  The server processes the request and returns JSON data.
  
  HTTP Methods:
  GET    = read / fetch data (no body sent)
  POST   = create new data (body with data sent)
  PUT    = update existing data (body with changes sent)
  DELETE = remove data

SLIDE 24 - REAL-TIME NOTIFICATIONS AND SLA MONITORING
------------------------------------------------------------------------

SOCKET.IO - HOW REAL-TIME WORKS:

  Old way (HTTP Polling):
  Browser asks server every 5 seconds: "Any updates?"
  Server: "No" | "No" | "Yes, here is the update"
  Wasteful and slow.

  New way (WebSocket / Socket.io):
  Browser connects ONCE -> connection stays open permanently.
  Server can push messages to browser ANY TIME.
  Like receiving WhatsApp messages - they arrive instantly.

  STEP-BY-STEP in Resolvex:
  1. User logs in -> browser calls socket.connect() to server
  2. Backend registers user: socket.join("user_" + userId)
     (creates a private "room" for each user)
  3. Admin assigns complaint to Electricity Board:
     -> Backend code: io.to("user_" + deptUserId).emit("notification", data)
  4. Electricity Board's browser receives "notification" event
  5. React event listener updates notification bell count (+1) INSTANTLY
  6. Toast popup appears: "New complaint assigned to you"
  7. Notification also saved to MongoDB for history

  Events used:
  - "notification"  : new notification for a user
  - "complaint_update" : complaint status changed

NODE-CRON - SCHEDULED BACKGROUND JOBS:

  What is node-cron?
  A package that runs JavaScript code automatically at scheduled times.
  Like setting an alarm for your server - it runs code when the timer fires.

  Cron expression syntax: "minute hour day month weekday"
  Example: "0 * * * *" means "at minute 0 of EVERY HOUR"

  THE SLA CRON JOB (runs every hour automatically):
  
  SLA = Service Level Agreement (maximum time to resolve a complaint):
    High priority   -> 3 days deadline
    Medium priority -> 7 days deadline
    Low priority    -> 14 days deadline
  
  Every hour the cron job:
  1. Queries MongoDB: find all complaints where status != resolved/rejected
  2. For each unresolved complaint:
     Check: Is today's date > slaDeadline?
  3. If YES and slaBreached is still false:
     -> Update: complaint.slaBreached = true
     -> Create notification for admin: "SLA breached for [complaint name]"
  4. Admin dashboard shows SLA Breached count in RED
  
  Why this matters:
  - Departments are held ACCOUNTABLE for resolving on time
  - Admin can see which complaints are overdue
  - Creates pressure to fix problems faster
  - Completely automatic - no human needs to manually check

CHALLENGE 1 - JWT Role-Based Authentication:
  Problem: Need different access for Citizen, Admin, Department. Complex to implement.
  Solution learned:
  - server/middleware/auth.js has two functions:
    protect(req,res,next): verifies JWT with jsonwebtoken.verify()
    authorize(...roles): checks req.user.role is in allowed roles array
  - Applied to routes: router.get("/", protect, authorize("admin"), controller)
  - In React: ProtectedRoute component wraps all role-specific pages
    If user role doesn't match -> redirect to /login
  KEY LEARNING: JWT-based stateless authentication + React protected routes

CHALLENGE 2 - Google Gemini AI Integration:
  Problem: Getting Gemini to return structured, consistent JSON was tricky.
  Solution learned:
  - Prompt engineering: tell AI exactly what format to return
    "Return ONLY valid JSON. No markdown. Fields: category, priority, confidence, suggestion"
  - Parse and validate the response before using it
  - Built a FALLBACK: if Gemini API key missing -> keyword-based mock classification
    This ensures app works in demo even without internet or API key
  KEY LEARNING: Prompt engineering + graceful degradation pattern

CHALLENGE 3 - Socket.io Real-Time Notifications:
  Problem: Making data appear on screen WITHOUT refreshing the page was a new concept.
  Solution learned:
  - Socket.io server: io = new Server(server, { cors: { origin: clientUrl } })
  - Socket.io client: const socket = io(serverUrl)
  - Rooms concept: socket.join("user_" + userId) -> private channel per user
  - Server emits: io.to("user_" + id).emit("notification", data)
  - Client listens: socket.on("notification", callback)
  KEY LEARNING: WebSocket event-driven programming + Socket.io rooms

CHALLENGE 4 - File Upload Pipeline:
  Problem: Multi-step process that can fail at any point - hard to handle errors.
  Solution learned:
  - Multer reads file from HTTP request (stored temporarily in memory or disk)
  - Cloudinary SDK: cloudinary.uploader.upload(buffer) returns URL
  - All steps wrapped in try-catch blocks
  - If Cloudinary fails -> error returned to client with clear message
  - Set strict limits: images max 5MB each, videos max 30MB
  KEY LEARNING: Multer middleware + Cloudinary integration + error handling

CHALLENGE 5 - SLA Cron Job:
  Problem: Running automatic background code without any user action.
  Solution learned:
  - node-cron package: cron.schedule("0 * * * *", async () => { ... })
  - Added a "running" flag to prevent multiple executions overlapping
  - Used Mongoose queries to find overdue complaints efficiently
  KEY LEARNING: Scheduled background jobs + cron expressions

CHALLENGE 6 - Responsive Modern UI:
  Problem: Making interface look professional and work on all screen sizes.
  Solution learned:
  - CSS Flexbox for flexible row/column layouts
  - CSS Grid for card-based layouts (complaint cards, dashboard cards)
  - Framer Motion: variants + animate props for smooth animations
  - Dark color theme with purple accents (HSL color values for consistency)
  KEY LEARNING: Modern CSS layout + animation libraries

  POSSIBLE EXAMINER QUESTIONS AND ANSWERS:

  Q: What language did you use?
  A: JavaScript for both frontend and backend.
     Frontend: React.js | Backend: Node.js + Express.js

  Q: What database did you use and why MongoDB?
  A: MongoDB - because it is a NoSQL database that stores data as flexible
     JSON documents. Since our complaint data can vary in structure
     (some have images, some have location, some are anonymous),
     MongoDB is more flexible than a traditional SQL database.

  Q: How does the AI work?
  A: We use Google Gemini API. When a citizen types a complaint,
     we send the title and description to Gemini with a structured prompt.
     Gemini returns JSON with category, priority, confidence score,
     and a helpful suggestion. We display this to the citizen.

  Q: How do real-time notifications work?
  A: We use Socket.io which creates WebSocket connections.
     Unlike normal HTTP, WebSocket keeps a permanent open connection.
     So when admin assigns a complaint, the server instantly pushes
     a notification event to the department's browser without any refresh.

  Q: How is security handled?
  A: Three layers:
     1. Passwords hashed with bcryptjs (never stored as plain text)
     2. JWT tokens for authentication (stateless, expires automatically)
     3. Role-based middleware (only correct role can access each route)

  Q: What is SLA and how does it work?
  A: SLA = Service Level Agreement (deadline to resolve complaint).
     High priority = 3 days, Medium = 7 days, Low = 14 days.
     A node-cron job runs every hour and checks if any unresolved complaint
     has passed its deadline. If yes, it marks it as "SLA Breached" and
     notifies the admin with a red alert on the dashboard.

  Q: How do file uploads work?
  A: The citizen selects photos/videos on the form.
     They are sent as multipart/form-data to the backend.
     Multer middleware reads the files.
     Files are uploaded to Cloudinary (cloud storage).
     Cloudinary returns a URL.
     The URL is saved in MongoDB alongside the complaint.

  Q: What is the difference between the three user panels?
  A: Citizen: reports problems, tracks own complaints only.
     Admin: sees all complaints, assigns to departments, manages users.
     Department: sees only their assigned complaints, resolves them.
     Access is controlled by JWT role field + middleware on every route.
